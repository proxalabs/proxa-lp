# Next.js + Payload CMS Migration — Design Spec

**Status:** Approved in chat 2026-11-14 ("that is right… start now"). Build in progress.
**Date:** 2026-11-14
**Branch:** `cleanup-root-files` (the user asked for all commits here; no new branch).

## Intent

Replace the Vite single-page app and its custom Firebase CMS with one Next.js app
that has Payload CMS inside it, and make the site as strong as it can be for search.

Why: the current site only looks server-rendered. A headless browser snapshots each
page at deploy time, so anything published between deploys is an empty shell to
crawlers, unknown URLs return 200, redirects happen in the browser, and no internal
link is a real `<a href>` (navigation is `onClick` on buttons and divs). The owner
also plans to host on AWS, where a Postgres-backed Payload fits and Firebase does not.

## Goals

1. Every public page is real server-rendered HTML with its content, meta tags and
   structured data in the response.
2. Content published in the CMS is crawlable immediately, without a deploy.
3. Same design and same URLs as today. A visitor or Google sees no change except
   speed and correctness.
4. Payload replaces the custom admin, Firestore, Firebase Auth/Storage and every
   Cloud Function.
5. Existing live content (four blog posts, Innovation Collective page copy) is in
   Payload.

## Non-goals

- **Deployment.** Nothing is deployed. No AWS work. The Firebase project is not
  touched. Media stays on local disk; S3 comes with the AWS work.
- Redesign or copy changes.
- Changing what the Firebase backend files in this repo do (`functions/`,
  `firebase.json`, `.firebaserc`, `firestore.*`, `storage.rules`, the Firebase seed
  and redirect-sync scripts, `deploy.yml`). They stay in place, untouched.

## Anti-goals

- Merging this branch to `main` before deployment is sorted. `deploy.yml` deploys
  `main` to Firebase Hosting and expects the Vite build; it must be replaced first.
- Losing a URL that is indexed today.
- Rebuilding the old admin feature-for-feature where Payload already has a native
  way to do the job.

## Decisions that are my call

- **Versions:** Next.js 16.4, Payload 3.93, React 19, Node 22.
- **Language:** new code (Payload config, routes, data layer) in TypeScript; the
  existing components stay `.jsx`.
- **Local database:** Postgres 16 in Docker on port **5433**, so it does not collide
  with the `proxa-forge` Postgres already on 5432.
- **Runtime-defined content types are dropped.** The old admin let a marketer define
  a new content type at runtime. None exist in production. In Payload a new type is
  a collection added in code.
- **Leads are stored.** Contact and newsletter submissions used to be email-only.
  They are now also saved (a `leads` collection) so nothing is lost when SMTP is
  down or unconfigured.
- **Rendering:** static generation with on-demand revalidation. Payload hooks
  revalidate the affected paths on publish, so pages are both cached and fresh.
- **`src/pages` is renamed to `src/views`** — Next.js would treat `src/pages` as its
  Pages Router.
- **Privacy / Terms footer links** stay inert (they are today) but lose their `href`
  so crawlers do not follow them to a 404.

## Architecture

```
Browser / crawler
      │
      ▼
Next.js app (one Node server)
 ├─ (frontend)  public site — server components read Payload's Local API directly
 ├─ (payload)   /admin UI and /api REST — generated by Payload
 └─ jobs        scheduled publishing (Payload jobs queue, cron inside the server)
      │
      ▼
Postgres  +  media on local disk (S3 later)
```

### Source layout

```
src/
  app/(frontend)/…      routes, layout, sitemap.ts, robots.ts, llms.txt, rss
  app/(payload)/…       Payload admin + API (generated files)
  payload.config.ts
  collections/  globals/  blocks/  access/  hooks/  endpoints/
  views/                the existing page components (was src/pages)
  components/           existing components
  content/              in-code default copy (the manifest) — unchanged
  lib/                  routes, content getter, data layer, SEO helpers
```

### Routes (unchanged URLs)

`/`, `/platform`, `/advisory`, `/ai-literacy`, `/insitex-lms`,
`/content-development`, `/the-lab`, `/about`, `/announcements`, `/resources`,
`/newsletter`, `/contact`, `/future-proof-your-organization`,
`/innovation-collective`, `/blog`, `/blog/[slug]`, `/news`, `/case-studies`,
`/case-studies/[slug]`, `/videos`, `/forms/[slug]`, `/search`, and `/[slug]` for
CMS-built landing pages.

Short links `/proxa-labs` → `/the-lab` and `/letsmeet` → `/contact` become permanent
server redirects.

### Navigation becomes real links

`setPage(page, {hash, slug})` (95 call sites, 32 files) is removed. A `hrefFor()`
helper maps the same page keys to URLs, and every navigational button/div becomes a
Next `<Link>` with the same class names. Dropdown menus are rendered in the HTML
(hidden until opened) so their links are crawlable.

### Fixed marketing pages

The model stays: in-code default copy, optional per-field override from the CMS.
Each of the 14 pages becomes a Payload **global** whose fields are generated from
the existing manifest (362 fields: text, textarea, image), plus an SEO tab (title,
description, image, hide from search). An empty field means "use the default".

Views take a `content` prop (the overrides) and build the same `c(key)` getter, so
the same code works as a server or a client component. Views with no interactivity
render on the server only.

### Payload content model

| Old (Firestore) | New (Payload) |
|---|---|
| `articles` | `posts` — Lexical rich text body with custom blocks (key takeaways, FAQ, image), category, tags, author, featured, order, SEO |
| `caseStudies` | `case-studies` |
| `videos` | `videos` |
| `pages` (section kit) | `pages` — `layout` blocks: hero, text+image, formatted text, feature cards, stat band, pull quote, CTA, FAQ, logo strip, form |
| `authors` | `authors` |
| `media` + Storage | `media` (uploads, required alt text, resized variants) |
| gated files | `files` (uploads, not publicly readable) |
| `forms` / `formsPublic` / `formSubmissions` | form-builder plugin: `forms`, `form-submissions` |
| `siteContent/<page>` | one global per fixed page |
| `siteContent/nav` | `navigation` global |
| `siteContent/redirects` | redirects plugin: `redirects` |
| `siteContent/blogSettings` | `categories` collection |
| `auditLog` | `activity-log` (written by hooks, read-only) |
| `contentTypes` / `content` | dropped (see above) |
| shared-password login | `users` with email + password, roles `admin` / `editor` |
| per-doc `versions` | Payload versions + drafts + autosave |
| `publishAt` + scheduled function | Payload scheduled publish (jobs queue) |

Access: public reads published documents only. Editors manage content. Only admins
manage users, navigation, redirects, the fixed-page globals and a page's custom-code
field — the same split the Firestore rules enforced.

Existing renderers (`ArticleLayout`, `CaseStudyLayout`, the section components) are
kept. Small adapters turn Payload documents into the shapes they already accept.

### Server endpoints (replacing Cloud Functions)

Same paths the front end already posts to:

- `POST /api/contact`, `/api/newsletter`, `/api/event-register` — validate,
  honeypot, rate-limit, store a lead, email the team.
- `POST /api/submit-form` — CMS forms: validate against the form, store the
  submission, email, return a short-lived signed download link if the form gates a
  file.
- `GET /api/gated-file` — serves a gated file for a valid signed token.

Email goes through Payload's nodemailer adapter with the existing `SMTP_*` /
`NOTIFY_EMAIL` variables. Rate limits keep the old numbers (12 per IP and 300
global per 15 minutes), stored in Postgres.

### SEO

- **Metadata API** on every route: title, description, canonical, Open Graph,
  Twitter card, robots. CMS values win over in-code defaults.
- **Structured data in the HTML:** Organization, WebSite (with site search),
  BreadcrumbList, BlogPosting, FAQPage, VideoObject, Service on the service pages.
- **`/sitemap.xml`** generated from Payload with last-modified dates, excluding
  anything hidden from search. **`/robots.txt`**, **`/llms.txt`** and a blog
  **RSS feed** generated the same way.
- **Correct status codes:** real 404s, permanent redirects from the redirects
  collection, no soft 404s.
- **Crawlable internal links** everywhere (above).
- **Fonts** self-hosted through `next/font` instead of a render-blocking Google
  Fonts `@import`.
- **Images:** explicit dimensions, lazy loading below the fold, a prioritised hero
  image, resized variants for CMS media.
- **Freshness:** publish, unpublish and edit revalidate the page, its index, the
  sitemap and the feeds.
- **Noindex** kept for `/future-proof-your-organization`, `/innovation-collective`,
  `/search`, `/admin`.
- Security headers carried over from `firebase.json`.

### Content import

A one-off script reads the live site's public data (the published articles query
the old prerenderer already used, and `/api/content`) and creates the four posts,
their authors and images, and the Innovation Collective overrides in Payload. It
only reads; it changes nothing on Firebase.

## Environment

`VITE_*` variables become `NEXT_PUBLIC_*`. New: `DATABASE_URL`, `PAYLOAD_SECRET`,
`PREVIEW_SECRET`. `.env.example` documents all of them.

Development uses Payload's automatic schema push. Production builds run committed
migrations first (`payload migrate && next build`), so a build needs a reachable
database.

## Verification

- `npm run lint` and `npm run build` pass.
- Every route above returns the right status, exactly one `<h1>`, a canonical, and
  valid JSON-LD in the server response (checked by fetching HTML, no JavaScript).
- Screenshots of each page match the live site at desktop and mobile widths.
- A post published in `/admin` appears on `/blog`, in the sitemap and the feed
  without a rebuild.
- Each form endpoint accepts a valid submission and rejects an invalid one.
